# Nova Agent 化演进产品需求文档（PRD）

> 版本：0.3（案例研究整合稿）  
> 日期：2026-11-20  
> 状态：已吸收定向案例研究结论；P0/P1 边界已收敛，仍待产品决策  
> 适用范围：基于 Nova 当前代码，定义学生日程助理的 Agent 化演进方向；本文不是已实施说明。

## 1. 执行摘要

Nova 不应成为又一个“什么都能聊”的通用聊天 Agent。产品应继续围绕学生的目标、日程与执行兑现：把用户提供的目标、可用时间、任务完成记录、偏差原因和明确画像，逐步转化为更适合这个用户的计划建议；用户确认后执行，再用真实结果修正后续建议。可控记忆是后续 P1 演进能力，不是 MVP 的隐含前提。

核心方案是“确定性业务内核 + 受约束 Agent 协调层 + 可追溯的用户数据闭环”。LLM 负责理解自然语言、补足信息和解释建议；排程、负载约束、可行性、重排、防雪崩规则仍由 Nova 的确定性引擎负责。记忆用于改善交互和建议，不自动训练模型、不自动改写生产代码，也不在未经同意时上传用户数据。

**差异化主张：不是更会说，而是守住用户认可的约束、能解释每次调整，并以实际执行结果逐步校准建议。长期方向是让用户可控的记忆提升相关性，但不把记忆或模型自主性当作产品价值本身。**

## 2. 需求标记与事实边界

本文每项能力按以下含义阅读：

- **现状**：已在 Nova 仓库实现，可由现有代码或文档核实。
- **建议**：本 PRD 提议建设，不代表已经实现或获批。
- **待决策**：影响产品范围或技术选型，需后续明确；当前不擅自补成结论。

## 3. 项目现状与问题

### 3.1 已有能力（现状）

- Nova 是面向学生的日程助理，采用原生前端、Node.js 22+、CommonJS 和零第三方依赖；支持浏览器本地运行及 Node HTTP 服务托管。
- 对话意图目前主要由关键词规则匹配；未命中时给出兜底，不调用大模型。
- 可行性评估、排程、四级重排、撤销、执行记录、偏差归因、中断挽救和周报主要由确定性引擎与现有业务流程完成；相同输入可复现，重排有确认、防护规则和快照回滚。
- 用户变更主要保存在浏览器 localStorage 的 `zx.overlay`；服务端另以按 userId 分区的进程内 Map 接收同步状态，服务进程重启会丢失服务端副本，但不等同于浏览器本地 overlay 同时丢失。当前已有演示账户、Bearer 凭证和同步接口，但没有注册、多用户账户体系或持久化数据库。
- 前端有本地引擎降级路径、离线状态、数据导出与删除能力。现状说明见项目 README、架构说明与前后端契约。

### 3.2 需要解决的问题

1. 固定关键词路由难以覆盖学生自然表达、上下文省略和连续追问；简单增加规则会持续扩大维护成本。
2. 当前执行数据能用于即时统计，但没有一套明确的画像、记忆采纳、纠正、过期和追溯机制，无法可靠地“越用越懂用户”。
3. 用户计划、实际投入与偏差原因尚未形成可解释的个性化校准流程。没有用户确认的历史规律，不应被当作事实。
4. 通用 Agent 的自由规划与自主工具调用可能削弱 Nova 原有的确定性、可撤销和边界清晰优势。
5. 当前本机存储与服务端内存存储有不同生命周期；数据同步、备份和跨设备体验仍需产品决策。

## 4. 产品目标与非目标

### 4.1 目标

- 让学生用自然语言完成目标设定、日程调整、执行记录和复盘，不必学习复杂命令。
- 分阶段建立可理解、可编辑、可删除、可追溯的用户画像与记忆治理闭环；MVP 先实现用户明确提供或确认的显式画像，记忆候选与跨会话检索属于 P1。
- 以用户实际执行数据改善后续计划建议，同时由确定性引擎持续掌握业务计算和硬约束。
- 保留轻量、可离线、低依赖、快速响应的体验；AI 能力不可用时，核心日程功能仍能工作。
- 以“计划是否更可兑现、用户是否理解并认可调整”为产品价值，而非对话长度、模型调用量或 Agent 自主程度。

### 4.2 非目标

- 构建可任意调用外部工具、可自行规划所有任务的通用 Agent 平台。
- 自动训练或微调基础模型、自动改写线上代码、自动调参生产规则。
- 在 MVP 中引入多 Agent 群体协作、后台自主长时间运行、社交/排行榜、课程内容市场或校园管理系统。
- 将 LLM 作为排程与可行性计算的权威来源，或以自然语言解释取代可验证的数据依据。
- 默认建立云端账户体系或跨设备同步；其范围与部署成本仍待决策。

### 4.3 本 PRD 的 MVP 边界

本文所称 MVP 只覆盖 P0 能力：在不破坏现有确定性业务流程的前提下，提供受限的自然语言入口、白名单工具、计划草案与确认、显式画像的基础治理、真实降级路径和最小流程追踪。模型是可插拔的理解/解释能力，不是 MVP 的运行前置条件；MVP 在未配置模型时也必须能完成核心日程流程。MVP 不以云端模型、持久化数据库、账号体系或跨设备同步为前置条件，也不包含记忆候选和跨会话记忆检索。

P1 能力（记忆候选、个性化校准、跨会话检索、数据导入和更完整的可解释复盘）必须在 P0 验证用户价值与数据边界后单独立项；若未被纳入某一版本，对应验收项标记为“不适用”，不得用部分实现冒充通过。

### 4.4 案例研究带来的产品约束

本轮对公开 GitHub 项目的定向核验表明，Nova 可借鉴的是可验证的产品与工程模式，不是案例自述的效果数字：

- **确定性生成器先行**：StudiPlan.ai 当前 V1 采用规则式 Smart Generator，LLM 仅作为后续方向。这支持 Nova 将模型放在理解/解释层，而不放进排程真值路径。
- **从“排得下”到“做得到”**：IntelliPlan 的 Follow-Through Engine 将执行历史、完成概率和局部计划修复分开描述，并强调重排前预览后果。对 Nova 的直接启发是：计划可行性、执行反馈和重排影响预览必须是不同的产品对象；但其概率模型、样本阈值和指标仍属于项目方自述，不能直接作为 Nova 的验收阈值。
- **透明启发式可作为基线**：Study Planner & Algorithmic Task Scheduler 采用多因素优先级、截止期紧迫度、每日容量和贪心分配，适合作为可解释的排程基线；Nova 仍须保留现有硬约束、锁定、缓冲位和回滚规则。
- **范围控制优先于集成数量**：案例中出现 LMS、Google Calendar、Notion 等扩展，但这些不是 Nova MVP 的必要条件；外部导入和同步继续放在 P1/待决策范围。
- **证据分层**：README、设计文档和源码只能证明项目方的实现或主张；未取得独立用户数据、第三方评测或可复现实验，因此本 PRD 不把上述案例的“效果”写成已验证事实。Reddit 与小红书本轮未取得可核验原帖，相关社区趋势不纳入本版结论。

## 5. 用户与关键场景

### 主要用户

有明确阶段性目标、需要安排每周学习时间、会遇到中断或任务偏差的学生。用户可能只有零散时间，也可能在准备考研、考公、课程项目等目标；产品不假设所有用户都有稳定作息或完整数据。

### 关键场景

**P0 场景（MVP）**

1. 用户提供目标、截止时间、基础情况与每周空闲时间，Nova 评估可行性并给出可调整的计划草案。
2. 用户临时有事或连续几天未执行，Nova 根据既有任务、时间约束与重排规则提出少量可解释选项，不擅自覆盖原计划。
3. 用户记录实际用时、完成度和偏差原因；Nova 将事实写入执行记录，并保留来源、版本和确认状态。

**P1 场景（不属于 MVP 默认验收）**

4. 用户记录积累到足够证据后，Nova 将可能的长期规律作为“记忆候选”供用户确认。
5. 用户再次制定计划时，Nova 只取与当前目标相关且仍有效的已采纳记忆，说明它如何影响建议，并允许用户忽略或纠正。

## 6. 产品原则与差异化设计

1. **确定性优先**：可行性、排程、容量、重排与回滚规则由 Nova 业务引擎计算；模型不能绕过硬约束。
2. **记忆有出处**：每条画像或记忆都能追溯到用户明确陈述、某次确认或具体执行记录；推断不得伪装成用户原话。
3. **少打扰、有用才行动**：只在缺少关键约束、将产生持久影响或存在高风险时请求确认；低风险解释不额外制造审批流程。
4. **用户可控**：用户能查看、改写、拒绝、删除、导出已纳入版本的画像或记忆，也能关闭个性化或云端模型处理；MVP 至少保证显式画像的逐项治理，P1 再扩展到记忆候选。
5. **本地优先，能力可降级**：模型、网络或持久化服务故障时，回退至现有规则路由与本地确定性引擎；明确提示降级状态，不伪称已完成云端处理。
6. **小而专**：Agent 聚焦“目标—计划—执行—复盘”闭环，不以增加 Agent 数量或工具数量作为先进性指标。
7. **先看影响再确认**：任何重排或放弃建议先展示变更差异、负载变化、受影响任务和可撤销路径；用户确认的是可理解的方案，不是黑箱动作。
8. **执行反馈不改写事实**：实际用时、完成度、偏差原因和用户的采纳/撤销行为作为事件保存；个性化只生成可审查建议，不静默修改硬约束或历史事实。

## 7. 需求范围与优先级

| P0 | 规则路由与 Agent 入口并存 | 先识别已有确定性意图与命令；自然语言解析只补足表达，不破坏旧路径；无法可靠识别时追问或兜底 | 建议新增 |
| P0 | 受限工具目录 | Agent 仅能调用白名单业务工具，如读取计划、评估可行性、生成重排草案、记录执行；不提供任意网络、文件、Shell 工具 | 建议新增 |
| P0 | 计划草案与确认 | Agent 生成有来源的输入摘要和业务引擎结果；写入、重排、放弃任务等有影响的操作必须遵守现有确认流程 | 建议强化/新增 |
| P0 | 影响预览与局部修复 | 重排先输出 diff、负载变化、受影响任务和回滚信息；优先修复受影响局部，不直接覆盖整周计划；无法满足硬约束时转为澄清或目标校准 | 建议强化 |

| P0 | 降级与隐私开关 | 无模型/无网络时使用现有功能；云端模型处理须单独说明，并由用户主动启用 | 建议新增 |
| P0 | 流程追踪与版本关联 | 记录请求、工具结果引用、引擎/规则版本、确认/撤销状态和失败状态；默认不记录完整提示词或原始敏感文本 | 建议新增 |
| P1 | 记忆候选与管理 | 从用户明确授权的数据形成候选；展示内容、证据和用途，经用户采纳后才成为长期记忆；支持拒绝、纠正、删除和过期 | 建议新增 |
| P1 | 执行反馈与个性化校准 | 将计划版本、实际用时、完成度、偏差类型和采纳/撤销结果关联起来；先生成校准建议，不静默改业务规则 | 建议新增 |
| P1 | 数据导入与结构化 | 支持用户主动导入常见任务表或学习记录；先预览、校验、映射，确认后再写入；具体文件格式待调研 | 建议新增 |
| P1 | 跨会话记忆检索与可解释复盘 | 按当前目标检索少量相关记忆，说明本次参考内容；区分事实、统计结果与推断，不将完整历史对话默认拼入模型上下文 | 建议新增 |
| 待定 | 登录、服务端持久化及多设备同步 | 需明确用户规模、托管方式、数据责任和成本后再定 | 待决策 |
| 待定 | 模型供应商、具体模型与云端部署 | 需根据隐私、延迟、可用性、费用与中国大陆访问条件做专项验证 | 待决策 |

## 8. 用户数据处理闭环

### 8.1 流程

以下流程分为两层：步骤 1—7 是 P0/MVP 的最小闭环；步骤 8—9 是 P1 在获得批准后对闭环的扩展。MVP 不因存在这些后续步骤而承诺记忆候选或跨会话检索。

1. **采集**：用户主动输入目标、时间限制、偏好、计划变更、执行记录；导入数据必须由用户主动选择。来源和时间随记录保存。
2. **解析**：意图路由先匹配 Nova 现有确定性命令；需要语义理解时才调用 Agent/模型。解析结果转成结构化草案，保留原始来源引用，不把模型输出直接视为事实。
3. **校验**：校验必填字段、时间范围、数据类型、与既有约束的冲突；业务计算交由现有确定性引擎。缺失信息导致计划差异明显时先询问用户。
4. **上下文组装**：MVP 只选择当前任务所需的用户明确提供/确认画像；P1 获批后才可额外选择少量相关且仍有效的已采纳记忆。两种情况下都要过滤已删除、已过期或与本任务无关的内容，默认不将完整历史对话发送给模型。
5. **建议与解释**：Agent 产出计划草案、工具调用理由和证据摘要；引擎返回确定性结果、负载变化、防护检查和撤销信息。分别标注“用户提供”“系统计算”“模型推断”。
6. **用户决策**：用户确认、修改、拒绝或撤销。未经确认不执行有持久影响的操作；当前重排确认与撤销能力应继续保留。
7. **执行与记录**：将用户实际完成情况和动作写成可追溯事件，记录计划版本、采纳/撤销状态、来源时间与规则版本；失败时不产生“已成功”假状态。
8. **复盘与候选更新（P1）**：系统从重复执行数据中计算候选规律，例如偏好时段或估时偏差；候选应有证据数量、时间范围和置信说明，必须经用户确认后才写入长期记忆。
9. **后续使用与治理（P0 画像治理 + P1 记忆治理）**：未来建议只能引用当前版本已允许使用的画像/记忆并显示依据；用户可改正、删除、导出或关闭个性化。删除应覆盖画像、记忆、关联索引和可恢复副本的既定生命周期，具体覆盖范围在持久化方案确定后定稿。

### 8.2 数据分类建议

| 类别 | 示例 | 建议规则 |
|---|---|---|
| 用户明确画像 | 时区、每周可用时间、偏好科目顺序、阶段目标 | 明确标注为用户提供；由用户编辑/删除；仅在相关任务中使用 |
| 业务事实与事件 | 任务估时、实际用时、完成度、重排确认/撤销 | 以业务记录为准，保存时间与计划版本；不由模型改写原始事实 |
| 记忆候选 | “晚上更容易完成长任务”等统计假设 | 标为推断候选，提供证据区间、置信度和有效期；经用户采纳后生效 |
| 对话内容 | 用户输入的自然语言 | 仅在当前功能需要时处理；默认不作为永久记忆，不默认上传或长期保留原文 |
| 认证与运行数据 | token、请求错误、性能计时 | 与模型上下文和业务记忆隔离；密钥不得进入提示词、日志或客户端持久化明文 |

### 8.3 记忆数据字段建议（P1，需在技术设计阶段定稿）

每条记忆至少应有：唯一标识、类别、内容、来源类型（用户明确/用户确认/统计推断）、证据引用、创建与更新时间、有效状态、置信说明、用户状态（候选/已采纳/已拒绝/已删除）、过期策略和格式版本。置信度不能单独作为采纳依据；低频、冲突或可能敏感的推断不自动生效。

## 9. Agent 开发框架与技术栈建议

### 9.1 建议架构

- **界面层**：保留当前原生前端、工作台和离线入口。Agent 是现有助理能力的补充，不要求为引入框架重写 UI。
- **路由层**：轻量 Router 组合规则匹配、上下文识别、结构化提取和澄清。确定性意图优先走旧业务流程；模型只处理规则覆盖不到且确有价值的理解任务。
- **工作流层**：把一个用户请求拆为有限状态的节点：意图识别 → 收集缺项 → 读取当前允许使用的画像（P1 再加入相关记忆）→ 调用白名单工具 → 校验 → 用户确认 → 写入事件 → 复盘。每一步有输入、输出、超时和失败状态；MVP 只要求跑通不依赖记忆的 P0 节点。
- **工具层**：将共享引擎和现有 API 包装为窄接口。工具参数用可验证结构；工具权限与用户身份绑定，模型不能构造任意用户 ID、绕过鉴权或写入确认未完成的数据。
- **业务内核**：保留 shared/engine 的纯函数与服务端校验，作为可行性、排程、重排及归因的权威实现。任何 Agent 流程均须使用同一业务规则。
- **记忆/持久化层**：抽象 profile、events、memory 的读写接口；MVP 可继续本地优先，避免把进程内 Map 误当长期数据库。新增持久化前明确数据迁移、备份、删除和恢复语义。
- **模型适配层**：封装供应商、超时、额度和错误处理；模型调用可被关闭，且不直接依赖模型专有响应格式。供应商与运行位置待决策。
- **评估与可观测性**：记录脱敏后的流程状态、工具结果引用、延迟、错误、确认/撤销结果和规则版本；默认不记录完整提示词或原始隐私内容。

### 9.2 技术栈提议及选型边界

| 层 | 当前基线 | PRD 建议 | 决策状态 |
|---|---|---|---|
| 语言/运行时 | JavaScript、Node.js 22+、CommonJS | 第一阶段沿用；新增模块继续遵循当前模块边界，避免为 Agent 化先做全栈重写 | 建议延续 |
| 前端 | 原生 JavaScript/CSS，支持 file:// 与离线降级 | 继续保留，不因模型流式输出强制迁移 SPA 框架 | 建议延续 |
| 业务计算 | shared/engine 纯函数 | 继续作为业务真值与模型调用失败时的兜底 | 硬约束 |
| Agent 工作流 | 目前无 Agent 框架 | 先以窄接口和可测试的有限状态工作流验证用户价值；当确有暂停/恢复、检查点和多步任务需求时，做 LangGraph.js 小型概念验证 | 候选，未批准 |
| 模型/工具调用 | 当前无模型 SDK 或外部服务 | 评估 Vercel AI SDK 的模型适配/工具循环能力，但只作为模型接入候选；禁止把开放式工具循环放进核心排程写路径 | 候选，未批准 |
| 持久化 | localStorage + 进程内 Map | 先定义存储接口与生命周期；MVP 保持用户可控本地存储。云端数据库、账号及同步均待决策 | 待决策 |
| 验证 | Node 内置测试 | 沿用 node:test；新增外部行为测试、隐私/删除测试、回放式工作流测试，不绑定具体 Agent 框架 | 建议延续 |

**推荐选型原则**：LangGraph.js 与 AI SDK 的职责不同，前者可用于显式状态和流程编排，后者可用于模型与工具循环；不应为了“前沿”而把多个 Agent 框架同时叠加。LangGraph.js 只在概念验证证明其暂停/恢复价值大于新增依赖、部署和维护成本后才纳入。若现有 Node/CommonJS 项目无法以低风险消费候选库，应保留内部工作流接口并重新评估，不进行大范围模块制式迁移。

**DeepSeek Super-agent 的借鉴边界**：仅借鉴“工具受控、工作按需触发、任务有隔离上下文、需要人处理的步骤显式暂停”等产品思路。DeepSeek 的 dsh-superagent-prototype 官方仓库明确标注为研究参考原型、非官方产品和非生产就绪软件，且不等同于相关论文的完整实现，因此不作为 Nova 的生产依赖或架构蓝图。

## 10. 关键用户故事

以下编号用于追踪范围：1—8、13、16—20服务于 P0/MVP；9—12、14—15属于 P1，不在 MVP 默认验收范围内。

1. 作为学生，我希望用自然语言描述目标和时间限制，以便快速得到可讨论的计划草案。
2. 作为学生，我希望看到可行性结论对应的输入和计算依据，以便判断是否需要调整目标。
3. 作为学生，我希望在关键字段缺失时只回答必要问题，而不是重复填写已有信息。
4. 作为学生，我希望 Nova 识别旧有的“今天学什么”“帮我重排”等请求，以便升级后原有操作仍可使用。
5. 作为学生，我希望模型无法使用时仍能查看和安排日程，以便网络波动不阻断核心功能。
6. 作为学生，我希望 Agent 生成重排草案而非直接覆盖日程，以便我确认后再承担计划变更。
7. 作为学生，我希望确认后可以查看变更、拒绝单项建议或撤销，以便保持对计划的控制。
8. 作为学生，我希望保存自己明确提供的可用时间和偏好，以便未来计划减少重复询问。
9. 作为学生，我希望区分“我告诉系统的事实”和“系统从记录中推断的规律”，以便纠正错误画像。
10. 作为学生，我希望看到记忆来自哪次记录、何时形成及为何被使用，以便判断其可信度。
11. 作为学生，我希望逐条批准或拒绝记忆候选，以便推断不会在我不知情时变成事实。
12. 作为学生，我希望修改或删除画像和记忆，并让后续建议不再使用已删除内容。
13. 作为学生，我希望记录实际用时、完成度和阻碍，以便复盘能依据真实执行情况而不是模型猜测。
14. 作为学生，我希望 Nova 从重复的估时偏差中提出调整建议，但不擅自修改引擎规则，以便我能审查校准依据。
15. 作为学生，我希望再次排计划时看到本次参考了哪些历史记忆，以便验证个性化是否真的相关。
16. 作为学生，我希望选择是否启用云端模型处理，并了解会发送哪些数据，以便对隐私和功能做知情选择。
17. 作为学生，我希望导出个人数据并清除历史记录，以便管理或迁移我的数据。
18. 作为产品维护者，我希望 Agent 工具均有清晰权限、输入校验与幂等行为，以便阻止误写、重复写和越权访问。
19. 作为产品维护者，我希望每次建议都能关联引擎版本、规则检查和用户确认状态，以便定位问题并回归验证。
20. 作为产品维护者，我希望通过真实任务闭环评估改进效果，而不是只用“回复像不像人”评价 Agent。

## 11. MVP 验收标准

以下为建议验收条件。MVP 默认只验收 P0 条目，并且在未配置模型时仍须通过核心流程；P1 条目只有在对应能力获批并进入版本范围后才纳入，否则明确标记为“不适用”。产品指标阈值需在基线测量后确定。

| 编号 | 验收条件 | 状态定义 |
|---|---|---|
| A1 | 现有目标评估、排程、重排、确认、撤销、执行记录、归因和周报在 Agent 变更后仍可用 | 通过/不通过；以现有测试与关键流程回归判定 |
| A2 | Agent 不能直接改写排程算法输出、跳过引擎约束或绕过确认流程 | 通过/不通过；构造越界、拒绝和重复提交用例 |
| A3 | 每次建议能区分用户输入、确定性计算与（若启用）模型推断，并说明所用关键约束 | 通过/不通过；按结果结构与界面展示检查；未启用模型时不得虚构模型来源 |
| A4 | 显式画像具有来源、状态和用户可编辑/删除路径；已删除项不再被使用 | 通过/不通过；端到端生命周期测试 |
| A5 | 记忆候选未经用户采纳不会成为长期有效画像；冲突记忆可被标记并要求澄清 | P1 纳入时通过/不通过，否则不适用 |
| A6 | 启用模型/API 时，超时、限额或格式错误有明确失败状态，并回退至本地能力或澄清流程 | 启用模型时通过/不通过；未启用时不适用 |
| A7 | 云端模型处理默认关闭或在用户明确选择前不发生；界面说明数据发送范围 | 通过/不通过；网络请求与设置状态核对 |
| A8 | 计划写入、含放弃项的重排及其他持久影响操作必须获得相应用户确认 | 通过/不通过；确认前后状态比对 |
| A9 | 关键流程事件能以关联 ID、时间、计划版本、规则/引擎版本和结果状态追溯；日志不泄露 token 和原始敏感文本 | 通过/不通过；日志检查与脱敏测试 |
| A10 | 无模型配置与离线模式下，核心业务仍可用且状态提示真实 | 通过/不通过；断网/禁用模型场景测试 |
| A11 | 导入数据（P1 扩展）写入前可预览、校验、取消；无效行不破坏已有数据 | P1 纳入时通过/不通过，否则不适用 |
| A12 | 统计或记忆建议有足够证据说明；样本不足时明确显示“待确认”而不是生成确定结论 | P1 纳入时通过/不通过，否则不适用 |
| A13 | 重排建议在确认前展示任务级 diff、负载变化、受影响的锁定/弹性约束和撤销路径；确认前不得改变持久状态 | 通过/不通过；对局部中断、超载和含放弃项场景检查 |
| A14 | 执行事件与计划版本关联，个性化建议不得改写原始执行事实或直接改变排程硬约束 | P0 事件关联通过/不通过；P1 个性化部分未纳入时不适用 |

### 当前实施状态

- 已确定：离线确认先在本地生效；联网后由服务端复核，冲突或方案变化时再次确认。基线缺失时不得静默提交。
- 已实现：在线确认后保存按身份隔离的进程内最小基线；尚未接通离线复核或普通新建计划的基线写入。
- **A1：不通过**——撤销可能覆盖后续任务状态，执行记录回读未闭合。**A2 / A8：不通过**——通用同步写入尚未绑定已确认的计划变更。**A14（P0）：不通过**——顺延状态尚未纳入计划版本。A5、A6、A11、A12 在当前范围内不适用。

### 建议观测指标

- 关键任务完成率：目标设定、生成计划、用户确认、执行记录、复盘的端到端完成比例。
- 建议采纳率与撤销/拒绝率：按建议类型区分；撤销率升高应视为质量信号，不追求单纯提高采纳率。
- 计划可兑现度：计划任务完成度、实际/估计时长偏差及连续中断情况，按用户和目标周期观察。
- 交互成本：完成目标设定与一次重排所需轮数、重复询问信息比例、等待时间。
- 记忆治理质量（P1）：候选采纳/拒绝、用户纠正、过期后仍被使用的次数；后者目标为零。
- 可靠性与成本（P0/P1）：模型调用失败率（启用模型时）、降级成功率、每个有效计划闭环的延迟与模型成本。未启用模型的 MVP 只统计本地流程延迟和降级/兜底可用性。

## 12. 测试策略

- **确定性引擎回归**：继续覆盖硬约束、边界输入、幂等、确认、快照撤销和防雪崩守卫；测试外部行为，不锁定私有实现细节。
- **Agent 路由测试**：覆盖规则命中、语义解析、缺项澄清、歧义、越权意图、模型不可用和不支持请求。
- **工具权限测试**：越权用户、无效参数、重复调用、确认缺失和部分失败均不能产生未授权状态变更。
- **记忆生命周期测试（P1）**：候选生成、采纳、拒绝、纠正、冲突、过期、删除、导出与后续检索逐环节验证；未纳入 P1 的版本标记为不适用。
- **数据闭环测试（P0 基线，P1 扩展）**：给定输入事件与规则版本可回放出同样的确定性计算；若启用模型，模型输出只作为建议，不覆盖事实事件。
- **隐私与安全测试**：验证默认云端关闭、数据最小化、token/敏感信息脱敏、删除语义与存储隔离。
- **降级测试**：模型超时、无网络、服务端重启和本地模式下核对可用能力与用户提示。
- **现有测试先验**：沿用项目 node:test 测试风格；当前已有 engine、API 和 mascot 测试。新增测试应关注用户可见行为与接口契约，不因选择某个框架而绑定其内部状态实现。

## 13. 分阶段建议

1. **阶段一：P0 契约与护栏**——先定义请求/草案/工具调用/确认/事件追踪的数据结构、权限边界、失败状态和版本关联；不接模型也能用现有确定性引擎验证写入保护与回滚。
2. **阶段二：P0 受限语义入口**——为自然语言解析定义可插拔的模型适配接口和工具白名单；先用现有规则/结构化解析跑通闭环，再在模型获批并启用时对照关键词路由验证是否减少重复提问；无论是否接入模型，都必须能回退到本地能力。
3. **阶段三：P1 画像与记忆治理**——先支持显式画像，再在数据量足够且有用户同意时生成记忆候选；逐步验证采纳、拒绝、纠正、过期、删除和相关性检索，不把推断静默写入长期事实。
4. **阶段四：P1 个性化校准与框架评估**——基于真实执行数据生成可审查的调整建议；并分别验证内部有限状态工作流与 LangGraph.js 的暂停/恢复、部署兼容、测试和额外维护成本，用结论决定是否引入依赖。
5. **阶段五：持久化/同步决策**——根据真实使用与部署方式再决定账号体系、服务端数据库、多设备同步、备份和恢复方案。

## 14. 风险与待决策项

| 项目 | 当前状态 | 决策影响 |
|---|---|---|
| 本地单机还是服务端账号化 | 待决策 | 影响持久化、认证、备份、删除和多设备同步；MVP 建议先保持本地优先 |
| 用户输入是否可发送至云端模型 | 待决策 | 影响知情同意、供应商选择、费用与隐私说明；默认应不发送 |
| 模型供应商、模型与访问网络 | 待决策 | 影响延迟、费用、数据处理协议和部署可靠性 |
| LangGraph.js 是否值得引入 | 待验证 | 需与内部有限状态工作流做小样本技术验证；不能仅凭功能清单决定 |
| 画像/记忆推断的证据门槛与过期规则 | 待决策 | 影响误记、过度个性化和用户信任；需基于数据质量测试制定 |
| 导入数据格式与范围 | 待决策 | 影响解析、安全校验、用户价值和测试复杂度 |
| 数据删除覆盖本机备份/服务器副本的语义 | 待决策 | 需与存储选型、恢复窗口和法律/运营要求一致 |

**主要风险控制**：模型幻觉用结构校验与确定性引擎约束；错误记忆用来源追溯、用户审核和删除机制；隐私风险用默认本地、最少上下文和显式云端授权；依赖膨胀用阶段门槛和单框架原则；服务重启丢数据的问题在决定持久化方案前明确展示，不以“Agent 记得”作不实承诺。

## 15. 范围外

- 自动执行不可逆的账户、支付、通知发送、对外通信或公开发布操作。
- 未经用户确认，把学习偏好或表现推断成固定人格标签。
- 将完整对话永久保存为长期记忆，或将用户数据用于基础模型训练。
- 引入多 Agent 自主协作作为 MVP 前提。
- 在本 PRD 阶段改代码、升级依赖、选择生产数据库、发布 GitHub Issue 或实施云端部署。
